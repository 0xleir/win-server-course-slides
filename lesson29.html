概念

Windows 自带日志 vs Sysmon

系统自带安全日志

  • 记录登录、权限、策略变更
  • 进程信息少、命令行默认不记
  • 攻击者的具体动作难还原

Sysmon（Sysinternals）

  • 记录进程创建的完整命令行
  • 网络连接、DLL 加载、文件/注册表改动
  • 攻击行为的"高清录像"
一句话：安全日志告诉你"谁登录了"，Sysmon 告诉你"登录后干了什么"。
Sysmon 是微软 Sysinternals 的免费工具，装成一个驱动+服务，把细粒度的系统活动写进自己的事件日志通道。它不替代安全日志，而是补充。强调它依赖一个配置文件 sysmon-config.xml 来决定记录什么、过滤什么，否则日志会爆炸。
任务 1 · 22′ · DC1

安装与验证 Sysmon

以管理员运行，使用教师预置的配置文件

C:\Tools\Sysinternals\Sysmon64.exe -accepteula -i C:\Tools\sysmon-config.xml

Get-Service Sysmon64
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -MaxEvents 5
验证：服务状态 Running，且能从 Sysmon 通道读出事件，说明部署成功。
-accepteula 接受许可，-i 安装并加载配置。sysmon-config.xml 由教师预置（常用社区配置如 SwiftOnSecurity 版本）。如果 Get-Service 找不到 Sysmon64，可能是用了 32 位的 Sysmon.exe，服务名会是 Sysmon。装好后 Sysmon 立即开始记录，后面任务 2 制造的活动就能被它捕获。
任务 1 · 概念

5 个必须记住的 Sysmon 事件 ID

Event ID含义排查用途
1进程创建看谁启动了什么、完整命令行
3网络连接发现外联、可疑端口
7镜像加载（DLL）发现 DLL 注入/劫持
11文件创建发现落地的恶意文件
13注册表值修改发现持久化（自启动项）
其中 Event 1（进程创建）信息量最大，是入侵分析的首选起点。
让学生把这 5 个 ID 抄下来，是本课必背内容。Event 1 的 CommandLine 字段能直接看到攻击者敲了什么命令，比如 whoami /all、net user /domain，这些都是侦察行为的标志。Event 3 能看到进程主动往外连，常用来发现 C2 回连。Event 13 结合 Run 键能发现持久化。

任务 2 · 分析

从 Sysmon 日志里找进程创建


Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" |
  Where-Object {$_.Id -eq 1} |
  Select-Object TimeCreated,
    @{N='CommandLine';E={$_.Properties[10].Value}} -First 20
找什么：命令行里出现 whoami /all、net user /domain、下载 .exe —— 都是侦察/落地的信号。
Event 1 的 Properties[10] 通常是 CommandLine 字段（下标随 Sysmon 版本略有不同，取不到可用 $_.Message 看全文）。让学生自己把刚才在任务 2 里敲的三条命令在这里找出来，建立"我做了什么 → 日志里长什么样"的直觉——这就是闭环：先以攻击者视角制造行为，再切回防御者视角去日志里找自己留下的痕迹。真实场景里，这些命令若不是管理员主动做的，就是入侵迹象。
任务 2 · 分析

安全日志里的可疑登录模式


$events = Get-WinEvent -FilterHashtable @{
  LogName='Security'; ID=4625; StartTime=(Get-Date).AddHours(-2)
}
$events | Group-Object {$_.Properties[19].Value} |
  Where-Object {$_.Count -gt 5} |
  Format-Table Count, Name -AutoSize
判读：同一来源在 2 小时内失败超过 5 次，高度可疑——很可能是密码攻击。
这是把第 28 课的技能复用过来：按来源 IP 分组统计失败登录，只保留超过 5 次的。StartTime 限定最近 2 小时，避免翻历史记录。阈值 5 只是示例，实际要结合业务基线。强调"异常"是相对正常基线而言的，所以平时就要知道正常长什么样。

概念：集中日志管理 WEF

SVR2日志源
→
DC1收集器
→
集中分析一处看全网

为什么要集中

  • 多台机器日志散落难关联
  • 被攻陷主机的日志可能被清
  • 集中后可统一检索、留证

两种订阅模式

  • 收集器发起：收集器主动去拉
  • 源发起：源主动推送到收集器
Windows Event Forwarding（WEF）是把多台机器的日志转发到一台集中保存。把日志集中到独立服务器还有一个安全意义：即使某台机器被攻陷、本地日志被清，收集器上的副本还在，能用于取证。两种模式的区别就是谁发起连接——源发起更适合大规模环境。
任务 3 · 18′

配置收集器与日志源

DC1 配置为收集器

wecutil qc                              # 快速配置收集器
wecutil cs C:\LabFiles\subscription.xml # 创建订阅（教师预置 xml）
SVR2（VM2）配置为日志源

winrm quickconfig
# 把 DC1 的计算机账户加入 "Event Log Readers" 组
wecutil qc 一键把 DC1 变成能接收转发的收集器；wecutil cs 导入订阅定义，subscription.xml 由教师预置，规定了收哪些机器的哪些日志。SVR2 侧 winrm quickconfig 打开 WinRM 服务，并把收集器（DC1）的计算机账户加进 Event Log Readers 组授权读日志。配置完成后在 DC1 的"转发的事件"日志里应能看到 SVR2 的记录流入。单机环境（无 SVR2）这部分只能做到第一步，check29.ps1 会诚实标记为无法验证。
排障

Sysmon / WEF 不工作？

现象原因处理
Get-Service 找不到 Sysmon64装的是 32 位版服务名改查 Sysmon
Sysmon 日志为空配置过滤太狠/没加载检查 -i 配置，必要时用默认配置
CommandLine 取不到Properties 下标随版本变改用 $_.Message
WEF 收不到源日志WinRM/组权限未配源上 winrm quickconfig，加 Event Log Readers
订阅状态 Inactivexml 路径或语法错核对 subscription.xml
最常见是 Sysmon 日志为空：要么过滤规则把一切都排除了，要么配置没真正加载。可以先用一个最小配置或 Sysmon 默认（不带 -i）确认能产日志，再逐步加过滤。WEF 的坑集中在 WinRM 和权限，源上一定要跑 quickconfig 并授权收集器账户读日志。
