概念 2

防火墙规则 vs 连接安全规则

防火墙规则（门卫）

  • 决定流量能不能进出：允许 / 阻止
  • 按端口、协议、IP、程序路径过滤
  • 不关心对方是谁、数据是否被偷看

连接安全规则（IPsec）

  • 决定怎么连：先验证身份，再加密
  • 本课用计算机身份 Kerberos V5
  • 本身不放行流量，仍需防火墙规则允许
一句话：防火墙规则管"能不能通"，连接安全规则管"通的时候安不安全"。
打个比方：防火墙规则是门卫查是否允许进入大楼，IPsec 是进门后用加密的专用通道说话。两者是配合关系，不是替代关系。Kerberos V5 认证依赖域，这也是为什么要先完成第 17 课的域搭建。

任务 1 · 27′ · DC1

精细入站规则：限制 SMB

Win+R›wf.msc›入站规则›审查三个配置文件的现有规则

New-NetFirewallRule -DisplayName "SMB-IT-Only" `
  -Direction Inbound -Protocol TCP -LocalPort 445 `
  -RemoteAddress 10.10.10.0/24 -Action Allow
New-NetFirewallRule -DisplayName "SMB-Block-Others" `
  -Direction Inbound -Protocol TCP -LocalPort 445 `
  -Action Block
想一想：第二条没写 -RemoteAddress，结合"阻止优先"，10.10.10.0/24 还能访问 445 吗？切到 CLIENT1 测试：Test-NetConnection 10.10.10.10 -Port 445
你在 DC1 上执行，然后切到 SVR2 上同步执行同样的配置。再到 CLIENT1 测试，结果会是 TcpTestSucceeded 为 False：阻止规则覆盖所有地址，优先于允许规则。这是本课最重要的"坑"，让学生自己发现再解释。观察完后按下一页的方法停用阻止规则，否则 DC1 的 SYSVOL、组策略和任务 2 的文件传输都会失败。
任务 1 · 27′ · DC1

按程序限制 · 出站规则 · 日志


Disable-NetFirewallRule -DisplayName "SMB-Block-Others"
$iis = "C:\Windows\System32\inetsrv\w3wp.exe"
New-NetFirewallRule -DisplayName "Allow-IIS" `
  -Direction Inbound -Program $iis -Action Allow
New-NetFirewallRule -DisplayName "Block-Outbound-Social" `
  -Direction Outbound -Protocol TCP -RemotePort 443 `
  -RemoteAddress "0.0.0.0/0" -Action Block -Enabled False
-Program：只放行这个程序监听的端口，换了程序就不通。
-Enabled False：出站规则先不启用，仅作演示，避免断网。
第一行是在原文基础上补充的：停用而不是删除 SMB-Block-Others，保留规则供检查和对比。按程序路径放行比按端口更精细：即使别的程序占用 80 端口也不会被放行。出站规则若启用，DC1 将无法访问任何 HTTPS 站点，所以原文要求先不启用；可在 wf.msc 出站规则里看到它呈灰色。
任务 1 · 27′ · DC1

开启防火墙日志


$log = "C:\Windows\System32\LogFiles\Firewall\pfirewall.log"
Set-NetFirewallProfile -Profile Domain `
  -LogAllowed True -LogBlocked True `
  -LogFileName $log -LogMaxSizeKilobytes 16384
Get-NetFirewallProfile -Profile Domain |
  Select-Object Name, LogAllowed, LogBlocked, LogFileName
参数含义
-Profile Domain只对域配置文件记录，DC1 内网网卡属于此文件
-LogBlocked True记录被丢弃的包，排障和发现扫描最有用
-LogMaxSizeKilobytes 16384日志上限 16 MB，写满后滚动
最后两行是补充的确认命令。日志不是实时显示的，要有流量才会写入，任务 3 中你用 Kali 扫描后就能看到大量 DROP 记录。常见错误：网卡实际处于公用配置文件，只给 Domain 开日志就什么都看不到，可用 Get-NetConnectionProfile 确认。
任务 2 · 27′ · DC1 + SVR2

创建连接安全规则

wf.msc›连接安全规则›新建规则›服务器到服务器
向导页DC1SVR2
终结点 1（本端）10.10.10.1010.10.10.20
终结点 2（远端）10.10.10.2010.10.10.10
要求要求入站和出站连接进行身份验证
身份验证方法计算机（Kerberos V5）
两端必须都配，而且方向相反。只配一端，两台机器之间会直接断开。
在 DC1 和 SVR2 上依次操作，填完一端立刻核对终结点是否对调。"要求入站和出站"意味着未经 IPsec 认证的流量全部被拒绝，所以先配好的一端会暂时连不上另一端，这是正常现象，等两端都配置完就恢复。配置文件页保持勾选"域"，名称可写 DC1-SVR2-IPsec 便于检查。
任务 2 · 27′ · DC1 + SVR2

验证 IPsec：SA 与 ESP


# 先在 DC1 上产生流量（访问 SVR2）
Test-NetConnection 10.10.10.20 -Port 445
Get-NetIPsecMainModeSA
Get-NetIPsecQuickModeSA

预期

  • 两条命令都返回 10.10.10.10 ↔ 10.10.10.20 的 SA
  • 主模式认证方式显示 Kerberos

Wireshark 观察

在 DC1 与 SVR2 之间复制文件，抓包过滤 esp，只见 ESP 包，看不到 SMB 明文

Test-NetConnection 一行是补充的，用来先产生流量，否则 SA 可能为空。Wireshark 在 C:\Tools\ 下，环境搭建时已下载。若 Wireshark 里仍能看到 SMB 内容，到 wf.msc 根节点属性 → IPsec 设置 → 自定义 → 数据保护，确认选的是"完整性和加密"而非仅完整性，这是很好的讨论点。
任务 3 · 13′ · Kali + DC1

用 Kali 扫描，回 DC1 看日志

在 Kali（10.10.10.50）上

nmap -sT 10.10.10.10 -p 21,80,443,445,3389,3390,5985,5986
切回 DC1 上

$log = "C:\Windows\System32\LogFiles\Firewall\pfirewall.log"
Get-Content $log -Tail 20
-sT：完整 TCP 三次握手扫描，会在目标日志里留下明显记录。
再次强调授权：nmap 只对 10.10.10.10 扫描。把每个端口的 nmap 状态填入记录表，并与本课规则对照。日志里 DROP 行的源地址应是 10.10.10.50，这就是"防守方发现扫描"的第一手证据。若读取日志提示拒绝访问，确认 PowerShell 以管理员身份运行。
预期结果

nmap 状态怎么读

nmap 状态含义日志里看到
open防火墙放行，且有服务在监听ALLOW TCP 10.10.10.50 → 10.10.10.10
closed放行了，但没有服务监听（收到 RST）ALLOW
filtered被防火墙丢弃，没有任何回应DROP TCP 10.10.10.50 → 10.10.10.10
对照记录：445 的结果取决于 SMB-Block-Others 此时是否启用；3389 与 3390 对照第 14 课改端口后的规则。
自己总结：哪些端口和预期不一致？为什么？例如 IPsec 规则只在 DC1 与 SVR2 之间要求认证，不影响 Kali 的扫描结果。结果因前面课程的配置而异，重点不是标准答案，而是能用规则和日志解释每一个状态。
排障

规则不按预期工作？

现象原因处理
IT 子网也连不上 445阻止规则优先于允许停用 SMB-Block-Others
DC1 与 SVR2 互相不通只有一端配了 IPsec 规则两端都配，终结点对调
SA 查询为空两端之间还没有流量先 Test-NetConnection 再查
pfirewall.log 没内容网卡不在域配置文件Get-NetConnectionProfile 确认
nmap 全部 filteredKali 不在 10.10.10.0/24Kali 上 ip a 确认 10.10.10.50
先让学生自己猜原因再翻出这一页。IPsec 配错导致 DC1 与 SVR2 断开时，最快的恢复方法是在 wf.msc 里先禁用一端的连接安全规则，而不是删除。规则太多分不清时，用 Get-NetFirewallRule -DisplayName "SMB*" 只看本课创建的规则。
